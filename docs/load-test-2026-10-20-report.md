### 1.4 失败根因

#### 1. 503 `cluster_state_unavailable`：CPU 过载的连带表现

1. 网关 CPU 接近 100% 后，goroutine 排队，读 Redis 响应也要排队。
2. 数据面每次访问 Redis 的预算是 200ms（`internal/cluster/client.go` 中的 `stateTimeout`），排队时间超过预算就报超时。
3. 凭证并发占位（`internal/cluster/credential_concurrency.go` 的 `Acquire`）拿不到状态，请求就被拒绝。亲和性查询同样超时，但它失败只降级，不报错。

Redis 本身很空闲。这个错误码在这里是误导：根因是网关过载，不是共享状态不可用。

#### 2. 503 `billing_unavailable`：同步余额查询在过载时超时

- 每个灵影 key 的请求都会同步调用 `POST /internal/aigw/balance`（`internal/integration/ly/admission.go`）。没有缓存，超时 3s，失败就拒绝请求。
- 失败日志里 status 都是 0，即超时或连接被关闭；出现时间和网关 CPU 打满重合，而灵影侧 p99 正常。判断主要是网关侧过载导致的，没有逐条核实。

#### 3. 灵影用量上报积压（压测中暴露的结构性问题）

- 每个计费请求结束后会往 PG 的 `ly_usage_reports` 写一行（`internal/integration/ly/report.go`）。
- 投递循环（`internal/integration/ly/deliverer.go`）在每个副本里是**串行**的：领取一条（UPDATE … SKIP LOCKED）→ 发 HTTPS 给灵影 → 删除，一次只处理一条。
- 实测：20:07–20:08，4 个副本合计约 42.5 条/秒（232168 → 229790，56 秒），即每个副本约 10 条/秒，期间没有投递失败。
- 压测后积压 233177 条，最早一条在 19:48 就该投递。缩回 2 个副本后约 21 条/秒，预计 3 小时左右才能消化完。
- 后果：
  - 积压期间灵影余额不扣减，余额检查一直能通过，存在超额消费窗口。
  - 每个请求在 PG 上多 3 条单行语句（插入、领取、删除），这是 PG CPU 从 28% 涨到 86% 的主要原因之一。
  - 只要持续负载超过 `10 × 副本数` RPS，积压就会无限增长。按目前 2 个副本，这个门槛只有约 20 RPS。

#### 4. 其他观察

- **超时长尾**：每档有 4–19 个请求超过 30 秒，网关日志里没有对应错误，像是上游流式响应挂住了，未深入排查。
- **日志丢失**：压测期间约 9% 的日志丢了（`request_completed` 约 18.7 万条，实际请求约 20.5 万；`billing_unavailable` 日志 92 条，客户端实际收到约 490 个）。原因是 awslogs 配置了 `mode: non-blocking` 和 25m 缓冲区，满了就丢。
- **自动扩容没有触发**：告警规则是 1 分钟平均 CPU 连续 3 个点超过 60%。R1 每档只有 30 秒，平均值分别是 36% 和 57%，一个点都没超过。即使触发了，新开实例也要 3–5 分钟。
- **19:44 的异常流量**：网关目标组在 19:44 一分钟内收到约 28.5 万个请求，都不是 2xx，网关日志里也没有对应记录，来源未查。

## 2. 稳定性修复建议

| 优先级 | 修复项 | 解决的问题 |
|---|---|---|
| P0 | 2.1 用量上报投递提速，并加积压告警 | 积压无限增长，余额扣减滞后 |
| P0 | 2.2 余额查询加短 TTL 缓存 | 每个请求都同步依赖灵影，过载时直接拒绝 |
| P1 | 2.3 实例级在途请求上限 | 过载时错误码有误导，还在浪费资源 |
| P1 | 2.4 降低单请求 CPU 开销 | 每个 vCPU 只有约 120 RPS |
| P2 | 2.5 高负载下日志不丢 | 排障依据不可靠 |

### 2.1 P0：用量上报投递提速，并加积压告警

**问题**：每个副本串行投递，约 10 条/秒，远低于请求速率。

**改法**：

1. 每个副本开多个投递 goroutine，并发数可配置（例如默认 16）。`claim` 已经用了 `FOR UPDATE SKIP LOCKED`，多个 goroutine 同时领取是安全的。
2. 投递成功后的删除改为攒批执行，减少 PG 单行语句。
3. 如果灵影能提供批量上报接口，改成一次领取 N 条、一次请求提交、一次批量删除，PG 和灵影的压力都会降一个数量级。这需要和灵影侧对齐。
4. 定时上报积压条数和最早一条的等待时长，作为 CloudWatch 指标，并配置告警（例如等待超过 5 分钟就告警）。

**验收标准**：

- 1000 RPS 持续 5 分钟期间，积压等待时长始终小于 1 分钟。
- 压测结束后 1 分钟内积压清零。

### 2.2 P0：余额查询加短 TTL 缓存

**问题**：每个请求都同步多一次灵影往返，过载时这一步超时就返回 503。

**改法**：

1. 按凭证缓存"可用且余额为正"的结果，TTL 5–10 秒；同一凭证的并发查询用 singleflight 合并成一次。
2. 只缓存"允许"的结果。key 无效、账户不可用、余额不足的结果不缓存，保证这些状态能立即生效。

**需要先确认**：缓存意味着最多 TTL 时长内的超额消费。可接受的超额窗口是多少，需要和灵影侧确认。

**验收标准**：同一 key 在 1000 RPS 下，每个副本每秒对灵影的余额请求不超过 `1 / TTL` 次。

### 2.3 P1：实例级在途请求上限

**问题**：过载时请求照单全收，先在 Redis 和余额查询上超时，再返回 503。错误码分别是 `cluster_state_unavailable` 和 `billing_unavailable`，排障时会被误导，而且每个被拒绝的请求在被拒绝前已经消耗了 CPU。

**改法**：

1. 在数据面入口加一个信号量，限制每个实例的在途请求数，可配置。参考值：R3 中 4 个任务在 1500 并发时仍然健康，即每个任务约 375 个在途请求。
2. 超过上限时直接返回 503，使用新的错误码（例如 `gateway_overloaded`），带 `Retry-After`。
3. 上报当前在途数，作为扩容和告警的依据。

**验收标准**：用 2 个任务在 2000 并发下重跑，错误码全部是 `gateway_overloaded`，被接受请求的首包 p99 和 1000 并发时相当。

### 2.4 P1：降低单请求 CPU 开销

**问题**：一个 `ping` 级别的流式请求，每个 vCPU 只能处理约 120 RPS，对一个代理来说偏重。真实 prompt 更长，容量还会更低。

**改法**：

1. 在单个任务上用 500 并发压测，同时采 30 秒 CPU profile（pprof）。
2. 按热点逐项优化。重点怀疑：每个请求的 JSON 日志、协议转换和序列化、和上游之间的 TLS、计费计算。

**验收标准**：单任务峰值吞吐提升，具体目标看 profile 结果再定。

### 2.5 P2：高负载下日志不丢

**改法**（二选一或组合）：

- 调大 awslogs 的 `max-buffer-size`。
- 降低每个请求的日志量，例如成功请求降级为 debug，或者按采样输出。

**验收标准**：1000 RPS 下，日志条数和 ALB 请求数的差距小于 0.1%。

## 3. 扩容方案

### 3.1 各组件容量与瓶颈顺序

| 顺序 | 组件 | 当前上限 | 依据 | 到达上限前的动作 |
|---|---|---|---|---|
| 1 | 灵影用量上报投递 | 约 `10 × 副本数` 条/秒 | 实测 42.5 条/秒（4 副本） | 先做 2.1，否则扩网关也没用 |
| 2 | 网关 CPU | 峰值约 240 RPS/任务；按 60% CPU 规划约 140 RPS/任务 | R1、R3 | 按 3.2 计算任务数 |
| 3 | PostgreSQL（m5a.large） | 约 1100 RPS | 约 960 RPS 时 CPU 86% | 先做 2.1 减少单行写入；仍然不够再升级到 4 vCPU 机型 |
| 4 | 灵影余额接口 | 未到上限 | 约 960 RPS 时 p99 不超过 1.45s，主机 CPU 24% | 做 2.2 后压力会大幅下降 |
| 5 | Redis | 远未到上限 | 约 960 RPS 时 CPU 最高 13% | 暂不处理；同一凭证的并发 key 会集中在一个节点上，留意热点 |

### 3.2 网关任务数估算

```
任务数 = max(2, ceil(预期峰值 RPS / 140))
```

- 140 RPS/任务对应 60% CPU，留出 40% 余量应对突发和新实例启动期间的流量。
- 至少 2 个任务，保证跨可用区高可用。
- 这个系数是用 `ping` 级别 prompt 测出来的。真实流量的 prompt 更长、输出更多，上线后要按实际 CPU 重新校准。

| 预期峰值 RPS | 任务数 | PG 是否需要升级 |
|---|---|---|
| ≤ 280 | 2 | 否 |
| 500 | 4 | 否 |
| 1000 | 8 | 需要先做 2.1，否则接近上限 |
| > 1100 | 按公式计算 | 必须先做 2.1，并升级 PG |

每个任务固定 8 个数据库连接，24 个任务（`MaxTasks`）合计 192 个，在 `max_connections=400` 以内。

### 3.3 自动扩容调整

现状：按 CPU 60% 跟踪，扩容冷却 60 秒，`TargetCapacity: 100`（不留空闲实例）。这套配置只能应对持续几分钟以上的缓慢增长。

| 调整 | 改法 | 效果 |
|---|---|---|
| 常驻容量按峰值配 | `MinTasks` 按 3.2 的公式设置 | 突发流量不依赖扩容 |
| 增加请求数扩容 | 新增 ALB `RequestCountPerTarget` 目标跟踪，目标值约 140 RPS × 60 = 8400/分钟/目标 | 比 CPU 更早反映流量，和 3.2 的估算口径一致 |
| 预留空闲实例 | capacity provider 的 `TargetCapacity` 从 100 降到 80 左右 | 扩容时不用等新实例开机，省下 3–5 分钟 |
| 已知高峰提前扩 | 用 scheduled scaling 在高峰前调高 `MinTasks` | 活动、发布等场景提前就位 |

### 3.4 后续压测方法

1. 在同区域的云主机上发起压测，不经过本机代理，也不受本机端口数限制。
2. 用修复后的压测工具，确认 ALB 每分钟新建连接数远小于请求数。
3. 压测前先把 `MinTasks` 调到目标值，等目标组全部 healthy 后再开始。
4. 每档至少 60 秒，用施压窗口内的完成数计算 RPS。
5. 同时观察网关 CPU、PG CPU、Redis CPU、灵影接口延迟，以及 `ly_usage_reports` 的积压条数。
6. 压测结束后，确认积压已经消化，并把 `MinTasks` 恢复原值。
