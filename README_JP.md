## GPT-Load を選ぶ理由

アプリケーション側で必要なのは、一つの Base URL と一つの AccessKey だけです。プロバイダー、アカウント、認証情報、モデル、ルーティングポリシーはすべて管理画面で設定します。

<img src="./screenshot/architecture-overview.svg" alt="GPT-Load の統合アクセスとアップストリームルーティング構成図" width="860">

- **単一ゲートウェイでネイティブプロトコルを維持** — 公式 API、クラウド基盤、モデルサービス、互換中継を一元管理しながら、クライアントは OpenAI、Anthropic、Gemini のネイティブインターフェイスをそのまま使えます。
- **API キーとサブスクリプションを統一管理** — Codex、Claude、Antigravity、Grok と API キーチャネルで、認証情報管理・スケジューリング・健全性管理を共通化します。
- **スケジューリングと障害分離を内蔵** — 複数認証情報のスケジューリング、設定可能なウェイト、リトライ、クールダウン、ブラックリスト、セッションアフィニティにより、過負荷や失効の影響を抑えます。

グループ優先度は符号付き 32 ビット整数で、既定値は 0、値が大きいほど優先されます。利用可能な最上位の階層を選び、同じ階層内でルート戦略、ソフトアフィニティ、重みを適用します。再試行可能な実行失敗では同じ階層の候補を使い切らず次の階層へ進み、最下位では残りの候補を試します。転送試行回数の上限は全階層で共通です。準備失敗では降格せず、認証更新は元の認証情報を先に再実行し、固定セッションの制約を維持します。優先度変更はクラスタ設定で伝播し、割り当て進捗はレプリカごとに保持します。
- **可観測で導入しやすく、データを自己管理** — 健全性、ルート、ログ、使用量、コスト概算を確認でき、PostgreSQL と Redis の上で動作し、認証情報は暗号化して保存されます。

### リクエスト内容の記録

管理者はアクセスキーごとに記録を有効にし、ログ詳細で元のリクエスト本文を表示・コピーできます。本文には会話、ツール呼び出し、画像、秘密情報が含まれることがあります。長すぎる内容は切り詰め、ログの保持期間に従って削除します。秘匿化エクスポートは常に本文を除外します。キーの利用者はログイン後に常駐通知と自分の記録を確認できます。API のみを利用するユーザーには別途通知してください。

アクセスキー画面では、無効・期限切れ・検索対象外のキーを含む全ページの既存キーの記録を一括で有効・無効にできます。有効化にはプライバシー確認が必要です。この操作は新規作成時の既定値を変更しません。グローバル設定 `default_access_key_record_request_body` は boolean で、既定は `false` です。有効化には同様の確認が必要です。新規作成・コピーではシステムの既定値を使い、コピー元の設定を継承しません。画面は既定値の取得成功後に作成を許可し、その後は下書きとユーザーの選択を維持し、明示的な値を送信します。

作成 API で `record_request_body` を省略すると、トランザクション内で既定値を読み取ります。明示値を優先し、冪等再実行では最初の結果を保持します。管理者専用の一括 API は `PUT /api/access-keys/record-request-body` です。`{"record_request_body":true}` または `false` を送り、応答データは `{"updated_count":N}` です。既定値は以後に作成するキーだけに適用します。記録を無効にしても既存の本文は削除しません。

### カスタム上流エラールール

全体またはグループ単位で `error_rules` を設定できます。上から順に照合し、最初に一致したルールを適用します。ステータスコードとキーワードの両方を指定した場合、両方の条件が必要です。キーワードは code、type、summary を個別に、大文字と小文字を区別せず照合します。グループのリストは全体のリストを置換し、空のリストはカスタムルールのみ無効にします。組み込み判定は維持します。

操作は再試行、認証情報またはモデルのクールダウン、ブラックリスト閾値までの失敗加算、現在のリクエストでのグループ除外です。既存の安全な再試行制約とレスポンス送信後の制約は維持します。通常の成功レスポンスは再分類しません。健全性は Redis で共有し、ルール設定は PostgreSQL の設定リビジョンで伝播します。各リストは最大 100 件、シリアライズした JSON は最大 65,535 バイトです。

新しいルールの保存前に全レプリカを更新してください。旧版は未知のグループ設定を拒否するため、保存後はイメージのみのロールバックはできません。

## クイックスタート

> [!WARNING]
> 1.x を使用している場合は、先に[「1.x からの移行」](#1x-からの移行)を確認してください。2.0 は 1.x データを開く・インポートする・その場で移行することはできません。

### 1. サービスを起動する

Docker と Docker Compose v2.24 以降が必要です。

```bash
git clone --depth 1 https://github.com/tbphp/gpt-load.git
cd gpt-load

cp .env.example .env
# .env に AUTH_KEY、ENCRYPTION_KEY、POSTGRES_PASSWORD を設定する。
# 各値は openssl rand -hex 32 で生成できる
docker compose up -d
```

3 つのいずれかが空の場合、Compose は不足している変数名を示して起動を拒否します。起動を確認します：

```bash
curl --fail http://127.0.0.1:3001/health
```

GPT-Load が PostgreSQL と Redis に接続できると、レスポンスに `"checks": {"database": "ok", "redis": "ok"}` が含まれます。どちらかが利用できない間は理由とともに 503 を返します。

<http://127.0.0.1:3001> を開き、`AUTH_KEY` でコンソールにログインします。

> 既定ではローカルアドレスのみを待ち受け、インターネットには直接公開されません。

### 2. 初期設定を行う

初期設定は 3 ステップです：

1. **チャネルを追加** — アップストリームサービスを選び、API キーを 1 つ以上登録します。サブスクリプションチャネルは画面の案内に従って OAuth 認可または認証情報のインポートを行います。
2. **Group を作成** — チャネルを選び、利用可能なモデルと実行ポリシーを設定します。
3. **AccessKey を作成** — アクセスを許可する Group とクライアントプロトコルを設定し、生成された AccessKey をアプリケーションに渡します。

グループの**全件操作 → ファイルからインポート**で UTF-8 の TXT、JSON、JSONL ファイルを選択します。1 行に 1 つの API キー、または値がすべて文字列の認証情報フィールドオブジェクト（例：`{"api_key":"sk-example"}`）を指定します。整形された JSON オブジェクトは 1 件として扱います。**すべてダウンロード**で取得したファイルも再インポートできます。1 回あたり最大 500 件で、ファイルの合計サイズとリクエストサイズはそれぞれ 32 MiB 以内です。超える場合は手動で分割してください。新しい認証情報の同時実行数は無制限（`0`）で、既存の重複はスキップします。サブスクリプションアカウントは従来の認可フローを使用します。

認証情報には任意の表示名を設定できます（最大 255 Unicode 文字）。空欄で保存すると表示名を削除します。表示名は認証情報のレコード単位で、識別情報、スケジューリング、同時実行数の上限を変更せず、変更はレプリカ間で伝播します。ログには現在の表示名を表示します。サブスクリプションアカウントは UI で既定でマスクされ、カードと詳細から明示的に表示できます。これは画面上のマスクであり、API の秘匿化ではありません。管理者向けレスポンスには元のアカウントを保持します。

<details>
<summary>サブスクリプションチャネルの OAuth コールバックポート</summary>

Codex、Claude、Antigravity の OAuth クライアントは固定のコールバックポートを使用します。Compose はそれらを `HOST` で設定したアドレスに公開し、既定値は `127.0.0.1` です。`HOST=0.0.0.0` を設定すると、これらのコールバックポートもホストの全ネットワークインターフェイスに公開されます。ポートはアップストリームのクライアント側で固定されているため、同一ホスト上で同時に実行できる既定の Compose インスタンスは 1 つだけです。

SSH やリモートブラウザ経由で操作する場合、ブラウザの `localhost` から GPT-Load に到達できないことがあります。その場合はコールバック URL 全体を認可ダイアログに貼り付けることでフローを完了できます。

## サポート範囲

### クライアントプロトコル

| プロトコル              | 主なエンドポイント                                                 |
| ----------------------- | ------------------------------------------------------------------ |
| OpenAI Chat Completions | `POST /v1/chat/completions`                                        |
| OpenAI Responses        | `/v1/responses` およびそのリソースパス                             |
| OpenAI Images           | `POST /v1/images/...`                                              |
| OpenAI Embeddings       | `POST /v1/embeddings`                                              |
| Rerank                  | `POST /v1/rerank`                                                  |
| Jev Decisions           | `POST /v1/systemone`                                               |
| Anthropic Messages      | `POST /v1/messages`                                                |
| Gemini                  | `/v1beta/models/...`                                               |
| Gemini Embeddings       | `POST /v1beta/models/{model}:embedContent` / `:batchEmbedContents` |

各チャネルは実行可能なプロトコルと機能を明示的に宣言します。GPT-Load はサポート対象の機能間で変換を行いますが、任意のプロトコル・任意の JSON を扱う汎用コンバーターではありません。

Embeddings には 2 つの独立したネイティブプロトコルがあります。`openai-embeddings`（`POST /v1/embeddings`）は OpenAI、OpenRouter、Vercel AI Gateway、OpenAI Compatible、New API、GPT-Load の API Key チャネルで、`gemini-embeddings`（`POST /v1beta/models/{model}:embedContent` と `:batchEmbedContents`）は Gemini、New API、GPT-Load の API Key チャネルで利用できます。リクエストとレスポンスは各プロバイダーのネイティブ形式のままです。Gemini チャネルはテキスト入力を `:batchEmbedContents` に変換することで `openai-embeddings` も受け付けます。`dimensions` と `float` / `base64` 出力に対応し、Token ID 入力には対応していません。1 リクエストあたりの件数上限は Gemini 側で検証されます。同じクライアントモデル名の背後にあるグループには同じ Embedding モデルを使用してください。異なるモデルのベクトルが混在するのを防ぐためです。サブスクリプションチャネルには対応していません。プロトコルフィルターを設定していない AccessKey は既存の「有効なプロトコルをすべて許可する」動作を維持するため、アップグレード後に両方の Embeddings プロトコルへのアクセス権も得ます。最小権限で運用する場合は、プロトコルフィルターを明示的に設定してください。

Rerank は独立した `rerank` プロトコルを使用し、OpenAI Compatible、New API、GPT-Load の API Key チャネルで `POST /v1/rerank` に対応します。リクエストには `model`、`query`、テキストのみの `documents` 配列を指定し、`top_n` や `return_documents` などの上流パラメーターも利用できます。ストリーミング、サブスクリプション、プロトコル変換には対応しません。OpenAI Compatible には完全な API プレフィックス（例：`https://host/v1`）、New API / GPT-Load にはゲートウェイのルートを設定します。上流は互換 Rerank API を提供する必要があります。プロトコルフィルターのない AccessKey は Rerank へのアクセス権も得ます。`search_units` など Token 以外の単位のみが返る場合は未計価とし、Token 数や無料リクエストとして扱いません。

CLIProxyAPI、New API、GPT-Load の API Key チャネルは、非ストリーミングの `POST /v1/alpha/search` と Responses 拡張パスの透過転送に対応します。Base URL はゲートウェイのルートを指定し、上流は対象 API を実装する必要があります。検索は `openai-responses` のプロトコルフィルターを使用し、検索レスポンス本文を保持します。レスポンス内の `usage` はモデルの Token 使用量や費用に計上しません。CLIProxyAPI と New API は `previous_response_id` と `store` を上流に転送できますが、保存済み Responses の取得・削除・キャンセル・入力項目 API は宣言しません。GPT-Load はこれらのリソース機能を維持します。

### 組み込みチャネル

- **公式・クラウド**：OpenAI、Anthropic、Gemini、xAI、Azure OpenAI、AWS Bedrock、Google Vertex AI
- **モデルサービス**：DeepSeek、Moonshot AI、SiliconFlow、Zhipu AI、Alibaba、Volcengine、OpenRouter、Cline、Groq、Vercel AI Gateway、Jev、Cerebras、Mistral、Nebius、Parasail、Wafer、Hugging Face（チャット）、Cohere（テキストリランキング）、OpenCode Go、OpenCode Zen、Modelflare
- **サブスクリプション**：Codex、Claude、Antigravity、Grok
- **カスタム**：OpenAI Compatible（任意の互換中継）

OpenCode Go / Zen は API キーと既存のマルチプロトコルゲートウェイアダプターを使用し、ネイティブ Chat Completions、ステートレスな Responses 作成、Anthropic Messages に対応します。ストリーミングとモデル検出も利用できます。上流モデルが対応するプロトコルを選択してください。自動プロトコル変換は行いません。カスタム Base URL には `/v1` を含めないゲートウェイのルートを指定します。Gemini ネイティブリクエストと Responses リソース操作は対象外です。Go クライアントはコーディングツールの識別情報と会話セッションヘッダーを保持してください。

### パラメーター上書きとプロトコル変換

配列内のフィールドには `*` を使用します：`{"remove":["/messages/*/reasoning_content"],"set":{"messages":{"*":{"tag":"gateway"}}}}`。ワイルドカードは既存の配列を走査し、存在しない配列の作成や要素の削除は行いません。各ルールは削除後に設定を適用し、後続ルールは変更後の値を参照します。明示的に削除したフィールドは DeepSeek の推論エイリアス補完で復元しません。上書き後の最終リクエスト上限は HTTP が 128 MiB、WebSocket が 10 MiB です。

グループのパラメーター上書きはプロトコル変換前に適用されます。通常のパラメーターはクライアント側の名前で指定します。例えば Responses の `max_output_tokens` は SDK により Anthropic の `max_tokens` に変換されます。Bifrost による会話プロトコル変換では、上書きで明示的に設定され、SDK のクライアントリクエスト構造にないトップレベルのフィールドを SDK の追加パラメーターとして渡します。保持されるかどうかは引き続き SDK の対象プロトコルへの対応に従い、任意のフィールドの透過転送は有効にしません。クライアントが付加した未知のフィールドは自動転送されず、既存のコンテンツブロック内のキャッシュ指定も従来どおりです。

例えば、Anthropic グループで Responses リクエストのキャッシュを指定できます。

```json
[{"match":{"protocol":"openai-responses"},"set":{"cache_control":{"type":"ephemeral"}}}]
```

キャッシュ設定を転送するもので、上流でのキャッシュヒットを保証するものではありません。

### データプレーンの同時実行数制限

全体・アクセスキー・グループの上限を同時に設定でき、既定はすべて無制限です。システム設定で全体の上限とアクセスキー・グループのデフォルト上限を指定し、個別に上書きできます。アクセスキーの空欄、グループの継承への復元はデフォルトを使用し、明示的な `0` は無制限です。いずれかの上限に達すると `concurrency_limit_exceeded` を即座に返し、待機や制限を回避するためのグループ・認証情報の切り替えは行いません。

全体とアクセスキーは未完了の論理リクエスト、グループは実行中の上流呼び出しを数えます。ストリーミングは転送終了まで、Responses WebSocket は実行中のターンごとに計数します。既存レスポンスのキャンセルは制限しません。カウンターは Redis に保持され全レプリカで共有されるため、各上限はデプロイ全体に適用されます。上限未設定のスコープは計数しません。設定変更でもリセットや実行中の処理の中断は行わず、管理リクエストとバックグラウンド処理は対象外です。Redis が利用できない場合、上限が設定されたリクエストは `503 cluster_state_unavailable` で拒否されます。管理 UI のホームに全体の現在値と有効な上限を表示します。アクセスキー一覧では有効な上限が 0 より大きい場合のみ同時実行数の上限タグを表示し、アクセスキーとグループの一覧にはリアルタイムの同時実行数を表示しません。

### アウトバウンドプロキシの一元管理

管理者はコンソールで PostgreSQL 内の暗号化プロキシカタログを管理します。追加、編集、インポート、有効化、無効化、削除、参照の確認、接続テストに対応します。HTTP と SOCKS5、およびユーザー名・パスワード認証をサポートします。グローバル設定、グループ、認証情報は ID でカタログのプロキシを選択します。AccessKey はプロキシ管理 API にアクセスできません。

選択順序は認証情報 → グループ → グローバル → 環境プロキシ → 直接接続です。無効化または削除後も参照は残りますが、上位レベルを継承するため、最終的に直接接続になることがあります。カタログの復号失敗は継承ではなくエラーになります。手動テストは無効なプロキシも含め指定したプロキシを直接使用し、Redis 上の全レプリカ共有の 8 枠を使います。データプレーンの枠は使いません。満杯の場合は 429、共有状態が利用できない場合は 503 を返します。保存するテスト URL は管理用の設定であり、実行時のルーティング設定ではありません。

### Codex クライアントモデルカタログ

管理者はモデル画面で Codex カタログのモデルを選択し、並べ替えられます。`GET /api/models/client-catalog` は候補、選択、既定のカタログ、モデル情報、バイト予算を返します。`POST /api/models/client-catalog/preview` は保存せずに下書きをプレビューします。`PUT /api/models/client-catalog` はカタログとモデル情報を 1 つの PostgreSQL 制御トランザクションでアトミックに保存し、全レプリカへ設定を伝播します。この 3 つの API は管理者専用で、AccessKey は利用できません。

- 候補は Responses create で呼び出せるモデルです。既定では `gpt-` で始まる名前を選択しますが、`gpt-image` と `gpt-image-*` は除外します。手動の順序を優先し、残りの GPT バージョンは新しい順に並びます。
- 保存とプレビューは JSON を厳密に解析します。未知のフィールド、重複フィールド、複数の JSON 値、不正なフィールド型は拒否します。リクエスト上限は 32 MiB です。`known_models` には前回取得した候補集合の全体を送信してください。候補集合が変わると古い下書きは `400 VALIDATION_FAILED` で拒否されるため、再取得してください。この任意の検査は設定バージョンのロックではありません。
- `models` は選択と順序を置換し、`[]` は選択を空にします。省略するとカタログを保持します。`reset_directory: true` はモデル情報を保持してカタログの既定値を復元し、空でない `models` とは同時に指定できません。`profiles` の各項目はモデル情報の上書きを全体置換します。`overrides: {}` は情報だけをリセットし、選択や順序は変更しません。`PUT /api/models/profile` も同じ規則です。
- 情報フィールドは `display_name`、`description`、`context_window`、`auto_compact_token_limit`、`supported_reasoning_levels`、`default_reasoning_level`、`input_modalities`、`service_tiers` です。常に標準ティアを既定とします。`priority`（Fast）と `ultrafast` はクライアントが明示的に選択します。`service_tiers: []` は高速ティアを非表示にします。API は `default_service_tier` を受け付けません。
- Codex レスポンスの上限は JSON の外枠を含め 1 MiB（1048576 バイト）です。超過時はカタログ順の先頭から収まる最大の完全な項目列だけを返します。項目の途中で切断せず、収まらない項目を飛ばして後続を追加することもありません。予算には選択全体のバイト数、実際のレスポンスのバイト数、各項目の収録状態を返します。配信予算を超える選択も保存できます。
- データプレーンの `client_version` が有効な 3 区分の数値で `>= 0.159.2` の場合、カタログから旧フィールド `base_instructions` を省略します。旧版や認識できないバージョンでは保持します。管理用プレビューは返された固定の `client_version` を使い、実際のバイト数は呼び出し元の権限とバージョンにも依存します。
- カタログ設定は Codex の表示だけに作用します。通常のモデル API、ルーティング、呼び出し権限は変更しません。データプレーンのカタログには AccessKey のプロトコル、モデル、グループ権限を引き続き適用します。システム通貨、クライアントモデルの統一価格、管理者限定の上流コスト表示も変更しません。

リクエストとレスポンスの構造は[制御 API 契約](docs/openapi.yaml)を参照してください。

> [!WARNING]
> 新旧ゲートウェイを混在させて設定を書き込まないでください。この機能はスキーママイグレーションを追加せず、既存の `client_model_overrides.overrides` JSON にカタログキー（`catalog_enabled`、`catalog_order`）と情報キーを追加します。旧プログラムは新しいキーを拒否します。保存後はイメージだけのロールバックでは復旧を保証できません。復元を検証した互換設定またはデータベースのバックアップと、それに対応するイメージを保持してください。

## デプロイとデータ

GPT-Load はコンテナとして動作し、PostgreSQL と Redis に依存します。`docker-compose.yml` は GPT-Load レプリカ 1 台、PostgreSQL、単一ノードの Redis を起動します。ロードバランサーの背後で複数レプリカを動かす場合は[マルチレプリカデプロイ](#マルチレプリカデプロイ実験的)を参照してください。

GPT-Load コンテナはステートレスで、ボリュームをマウントしません。設定と使用量は PostgreSQL に、共有される実行状態は Redis に保存されます。Compose はそれぞれを `postgres-data` と `redis-data` の名前付きボリュームに保存し、Redis は AOF 永続化と `maxmemory-policy noeviction` で動作します。

> [!IMPORTANT]
> `ENCRYPTION_KEY` はチャネル認証情報、プロキシカタログ、プロキシ参照の復号に使われます。PostgreSQL と `ENCRYPTION_KEY` は**必ず一緒にバックアップ**してください。鍵を失ったり置き換えたりすると、既存の暗号化済み認証情報は復元できません。また現行バージョンはマスターキーのローテーションに対応していません。

同梱のサービスの代わりに既存の PostgreSQL や Redis を使う場合は、`gpt-load` サービスの `DATABASE_DSN`（例：`postgres://user:password@db.example:5432/gpt_load?sslmode=require`）と `REDIS_ADDRS` を上書きしてください。

> [!WARNING]
> プロキシカタログへのアップグレード前に、PostgreSQL と `ENCRYPTION_KEY` を一緒にバックアップし、独立したデータベースで復元を検証してください。マイグレーション `0028_proxy_catalog` はカタログを作成し、コントロールプレーンの起動時に既存の暗号化プロキシ URL を暗号化 ID 参照へ変換します。スキーマと暗号化参照形式は旧バージョンと互換性がありません。すべての旧ゲートウェイを停止してから新バージョンを起動し、新旧混在のローリングアップグレードは行わないでください。イメージだけを戻しても復旧できません。ロールバックには復元を検証した更新前のデータベースバックアップ、元の鍵、対応するイメージを使用してください。

よく使う運用コマンド：

```bash
docker compose logs -f      # ログを確認
docker compose pull && docker compose up -d   # 最新の 2.x イメージへ更新
docker compose stop         # サービスを停止
```

公式 Compose は `ghcr.io/tbphp/gpt-load:2` を使用します。GA 前の `2` は検証済みの 2.0 Beta / RC を追跡し、GA 後は安定版 2.x のみを追跡します。イメージの完全なタグからは Git tag の `v` 接頭辞を除き（例：`2.0.0-beta.25`）、`2.0-beta` は 2.0 Beta チャネルとして残します。`latest` は引き続き 1.x を指します。GPT-Load はコンテナイメージとしてのみ配布されます。

## マルチレプリカデプロイ（実験的）

複数の GPT-Load レプリカが同じ PostgreSQL と Redis を共有し、ロードバランサーの背後で水平スケールできます。既定の `docker-compose.yml` は、同じ構成をレプリカ 1 台で動かすものです。

### 前提条件

- PostgreSQL（18 で検証済み）。
- Redis 7.0 以降（7.4 で検証済み）。単一ノードと Redis Cluster のどちらでも使えます。Redis Cluster では `REDIS_ADDRS` にすべてのプライマリを列挙してください。アドレスが 1 つだけの場合は単一ノードとして扱われ、他のノードにあるデータへのアクセスが失敗します。
- Redis には `maxmemory-policy noeviction` を設定し、AOF 永続化を有効にすることを推奨します。
- すべてのインスタンスで同じ `AUTH_KEY` と `ENCRYPTION_KEY` を明示的に設定してください。`INSTANCE_ID` はインスタンスごとに一意で、既定値は `<ホスト名>-<ランダム文字列>` です。
- 各インスタンスの時刻は NTP で同期してください。

### Compose サンプルで起動する

`docker-compose.cluster.yml` は nginx、GPT-Load レプリカ 3 台、プライマリ 3 台の Redis Cluster、PostgreSQL を起動します。Docker Compose v2.24 以降が必要です。

```bash
cp .env.example .env
# .env に AUTH_KEY、ENCRYPTION_KEY、POSTGRES_PASSWORD を設定する
docker compose -f docker-compose.cluster.yml up -d
curl --fail http://127.0.0.1:3001/health
```

nginx は `HOST`（既定 `127.0.0.1`）の `PORT`（既定 `3001`）で公開されます。レプリカを増やすには `gpt-load-N` サービスを複製し（`INSTANCE_ID` を変更）、`deploy/cluster/nginx.conf` の `upstream` に 1 行追加します。サンプルの Redis にはレプリカがないため、どのノードが故障しても共有状態が使えなくなります。本番環境ではマネージド Redis を使うか、各プライマリにレプリカを追加してください。

### ロードバランサーの要件

- スティッキーセッションは不要です。
- ネイティブ Responses WebSocket（`GET /v1/responses`）には `Upgrade` と `Connection` ヘッダーの転送が必要です。また `Host` は変更せずに渡してください。ゲートウェイはこれを使ってブラウザの `Origin` を検証します。
- SSE をチャンクごとに転送するためレスポンスのバッファリングを無効にし、長時間の生成と WebSocket セッションに足りる読み取りタイムアウトを設定してください。サンプルは 1 時間です。
- 準備完了プローブには `GET /health` を使ってください。データベースと Redis の両方を確認し、どちらかが利用できない場合は理由とともに 503 を返します。

設定全体は `deploy/cluster/nginx.conf` を参照してください。

### データベース接続

各インスタンスは最大 `DATABASE_MAX_OPEN_CONNECTIONS`（既定 `10`）の接続を開くため、合計はレプリカ数 × この値となり、PostgreSQL の `max_connections` 未満に収める必要があります。PgBouncer を使う場合は session モードにしてください。起動時のマイグレーションはセッションレベルの advisory lock に依存しており、transaction モードは未検証でサポート対象外です。

### サブスクリプションアカウントの認可

Codex、Claude、Antigravity の OAuth クライアントは固定ポートの `localhost` にコールバックするため、ロードバランサー経由ではインスタンスに届きません。そのためクラスターサンプルはこれらのポートを公開しません。ブラウザでサインインした後、アドレスバーの完全なコールバック URL を認可ダイアログに貼り付けてください。認可状態はデータベースに保存されるため、どのインスタンスでも完了できます。

### 共有される動作と既知の制限

- 設定変更、AccessKey の RPM 制限・コスト上限、認証情報のヘルス（クールダウン、ブラックリスト、失敗回数、モデルクールダウン）、サブスクリプションの認可状態、Responses の所有情報（`previous_response_id` による継続）、ソフトアフィニティをインスタンス間で共有するため、ロードバランサーにスティッキーセッションは不要です。設定変更は通常 1 秒以内に他のインスタンスへ反映され、届かなかった通知は 30 秒ごとのポーリングで補われます。同じサブスクリプションアカウントのリフレッシュは、クラスター内で同時に 1 インスタンスだけが実行します。
- 認証情報の同時実行数の上限（新しい UI の認証情報詳細で設定、0 は無制限）は全インスタンス合計で数えます。その認証情報へ同時に送られるアップストリームリクエストは合計で上限を超えず、ストリーミングリクエストはストリームが終わるまで枠を占有します。認証情報が上限に達している場合、リクエストはリトライ回数を消費せずに空きのある別の認証情報へ回ります。候補がすべて上限に達している場合は、ゲートウェイ内で待たせずに 429 `credential_concurrency_limited` と `Retry-After: 1` をすぐに返します。クラッシュしたインスタンスが占有していた枠は約 30 秒以内に解放されます。WebSocket セッションは枠に数えません。
- 保持期間のクリーンアップ、操作結果の圧縮、検証プローブ、Models.dev の自動同期は周期ごとに 1 インスタンスだけが実行し、手動同期とグループや設定の変更による同期は変更を受けたインスタンスで実行されます。Models.dev カタログは Redis で共有され（カタログ本体とほぼ同じサイズ、最大 32 MiB）、初回起動時は各インスタンスが 1 回ずつ取得します。
- 管理認証の失敗によるロックアウトは全インスタンスに適用され、TCP 接続元アドレスごとに数えます。ロードバランサーの背後ではロードバランサーのアドレスになり、すべての管理者が同じカウンターを共有するため、管理画面へのアクセス元はネットワーク層で制限してください。Redis が利用できない間は各インスタンスが個別に数えます。
- `affinity_capacity` は効果がなく、設定変更でもソフトアフィニティはクリアされません。`affinity_ttl` を短くした場合は既存のエントリにも即座に適用されます。
- ローリングアップグレード中に旧バージョンのインスタンスで作成された Responses は、それを保持していないインスタンスでは継続できません。
- Redis が利用できない場合、RPM 制限またはコスト上限を設定した AccessKey のリクエストと、同時実行数の上限を設定した認証情報を選んだリクエストはアップストリームへ転送されず、503 `cluster_state_unavailable` を返します。継続リクエストと `store` の Responses も 503 を返します（どのインスタンスでも継続できない ID を渡さないようレスポンスは返されません）。ソフトアフィニティは通常のスケジューリングに戻ります。認証情報のヘルスの変更はまずそのインスタンスで適用され、Redis の復旧後は Redis の状態が優先されます。
- Redis のデータが失われた場合、使用済みコストは最後のデータベースチェックポイント（約 1 秒前）に戻ります。
- コスト上限は計上済みのコストで判定され、コストはレスポンスを送信した後に計上されます（Redis の往復が 1 回増えます）。そのため、直前のレスポンスの直後に送られたリクエストや処理中の並行リクエストによって、使用済みコストが上限をわずかに超えることがあります。
- メモリの見積もり：`store` の Responses は `RESPONSE_BINDING_TTL` の間 1 件につき Redis キーを 1 つ使い約 0.25 KB（自動モデル選択を伴う場合は約 0.5 KB）、ソフトアフィニティは `affinity_ttl` の間 1 件約 0.3 KB です。「1 日の `store` レスポンス数 × TTL 日数 × 0.25〜0.5 KB」で見積もってください。
- 認証情報のヘルス統計ページとスケジューリングの公平性台帳は、そのインスタンスのビューです。
- サブスクリプションアカウントをリフレッシュ中のインスタンスがクラッシュした場合、そのアカウントは約 60 秒以内（リース TTL とポーリング 1 周期）に `outcome_unknown` になり、手動での復旧が必要です。
- WebSocket の接続数上限はインスタンスごとに適用されるため、N 台のインスタンスでは AccessKey ごとに最大 N 倍の接続を開けます。WebSocket セッションは受け付けたインスタンスに固定され、そのインスタンスを再起動または削除するとセッションは切断されます。

### 受け入れ検証を実行する

以下のコマンドは同じサンプル上で実行され、Docker と Compose v2.24 以降が必要です。

- `make cluster-e2e`：実際の 3 ノード Redis Cluster に対してデータベースと Redis の契約テストを実行し、RPM 制限が上限ちょうどを許可すること、コスト上限を超過しないこと、設定変更が 1 秒以内に伝わること、WebSocket が nginx 経由で接続できることを確認します。CI はすべての PR で実行します。
- `make bench-cluster`：上記に加えて、3 レプリカのクラスターと単一ゲートウェイのスループットと p99 レイテンシを比較します。各ゲートウェイは既定で 1 CPU に制限され（`GATEWAY_CPUS`）、すべてのコンテナがホストを共有するため、8 CPU 以上のホストで実行してください。

## 本番運用の注意事項

- 既定では `127.0.0.1` のみを待ち受けます。リモートアクセスが必要な場合は、管理されたネットワークまたは TLS 対応のリバースプロキシ経由で公開し、ACL とファイアウォールを設定してください。
- `AUTH_KEY` と `ENCRYPTION_KEY` は厳重に管理し、実際のキーをリポジトリ、ログ、スクリーンショット、公開 Issue に含めないでください。
- 既定の Compose は**レプリカ 1 台**で動作します。複数レプリカでの運用は[マルチレプリカデプロイ（実験的）](#マルチレプリカデプロイ実験的)を参照してください。
- 使用量とコストはアップストリームの応答に基づく**概算**です。運用分析やリソース評価には使えますが、プロバイダーの請求書や会計上の照合結果とは一致しません。
- システム通貨（全体設定 → 通貨と課金）は米ドルまたは人民元を選べます。人民元では「1 USD = X CNY」の為替レートを設定します。アップストリームの価格は常に米ドルです。各リクエストは精算時の通貨とレートで米ドル額と現地通貨額の両方を記録するため、レートを変更しても以降のリクエストにのみ影響し、過去の料金は書き換わりません。管理 API、UI、429 応答はシステム通貨で金額を返します。通貨を切り替えると、すべての AccessKey の料金上限が為替レートで新しい通貨に換算され、使用済み額はリセットされます。使用量の合計は現在の通貨のみを集計し、他の通貨の履歴があることを表示します。
- 各リクエストは 2 つの金額を計算します。**料金**はリクエストモデル（ClientModel）の統一料金に AccessKey 倍率を掛けたもので、料金上限と使用量集計に使います。**上流費用**はチャネルの上流モデル価格にグループ倍率を掛けたもので、ゲートウェイが上流に支払う費用であり、管理者にのみ表示されます。統一料金は「モデル」ページでリクエストモデルごとに設定し、すべてのグループとチャネルに適用され、段階料金と Fast・Ultrafast モード料金に対応します。統一料金が未設定のモデルは未計価として扱い、上流価格には戻りません。auto モデルは選択されたターゲットモデルで課金します。
- サブスクリプションチャネルはアップストリームの OAuth と互換プロトコルに依存し、アップストリームの変更に伴って調整が必要になる場合があります。利用権限のあるアカウントのみを接続し、各プロバイダーの規約に従ってください。
- 推論強度の更新に対応する Codex モデルでは、HTTP と WebSocket の `configuration_update` を保持します。Codex CLI では `--enable reasoning_effort_override` を有効にしてください。ゲートウェイ側の実験用スイッチは不要です。WebSocket のログは、同じ接続・モデルで直前に完了を確認した親レスポンスからのみ更新を引き継ぎます。未知のモデルと仮想フォールバックモデルはこの機能への対応を宣言しません。トークン由来のプランは表示用の補足情報で、実際の観測を優先し、利用可能なクォータを保証しません。詳細は [Codex の共通機能](third_party/cpaembedded/README.md#shared-codex-capabilities)を参照してください。
- Responses の `previous_response_id` による継続は、ネイティブ Responses と上流での状態管理を宣言した経路に自動で適用されます。現在は `openai`、`gpt_load`、`xai`、`newapi`、`cliproxyapi`、`sub2api` が該当します。帰属を AccessKey ごとに分離し、現在のルーティングで許可される元の認証情報へ固定します。ソフトアフィニティ設定には依存せず、状態が実際に利用できるかは上流に依存します。ステートレス応答と変換された応答は登録せず、Codex サブスクリプションの WebSocket 継続はまだ接続していません。アップグレード前やゲートウェイ外で作成されたものを含め、不明な ID は拒否されます。Group のパラメータ上書きでこのフィールドを変更することはできません。
- `empty_response_retry` は既定で無効です。グループで明示的に設定した値がグローバル設定より優先されます。有効にすると、ストリーミングの対話リクエストはクライアントへ確定する前に上流が内容を生成したかを確認します。上流が自然に終了したのに何も生成しなかった場合はその試行を失敗として次の候補で再試行しますが、認証情報のクールダウンやブラックリスト登録は行いません。再試行を使い切った場合は、上流が返した空の応答をそのままクライアントに渡します。出力上限の到達、コンテンツフィルター、拒否など終了理由で説明できる空の結果は再試行せずにそのまま返します。プリウォーム（`generate:false`）、`previous_response_id` または `conversation` を含むリクエスト、対話以外のエンドポイント、WebSocket は判定の対象外です。上流が内容のないイベントを送り続ける場合は、内蔵の上限で通常どおり確定し、応答を保留し続けることはありません。再試行で破棄された空の試行も上流では課金されますが、使用量とコストの概算には最終的に返した試行だけが記録されます。
- Codex WebSocket は `response.interrupt` に対応し、現在の接続で生成中の `response_id` だけを中断します。制御メッセージは推論 RPM、同時実行枠、リクエストログを追加しません。中断の送信が成功し、対応する終端イベントの `incomplete_details.reason=interrupted` を確認すると、元のリクエストを成功として記録し、実際の使用量で課金します。同じ接続でその ID から継続できます。クライアントへ返す `incomplete` 終端イベントは変更しません。要求していない中断や別の未完了理由は、引き続き未完了として記録します。
- `conversation` とその他の既存リソース ID はこの帰属ルーティングの対象外であり、単一の認証情報またはアップストリームでの認証情報間のリソース共有が引き続き必要です。

## 1.x からの移行

> [!WARNING]
> GPT-Load 2.0 は完全な書き直しです。1.x のデータを開く・インポートする・その場で移行することは**できません**。

2.0 は独立したデータベース、ポート、Docker ボリュームでデプロイしてください。検証完了後に本番トラフィックを切り替え、ロールバック期間が終了するまで既存の 1.x 環境を保持してください。1.4.x メンテナンスラインのドキュメントは[公式ドキュメント](https://www.gpt-load.com/docs?lang=ja)にあります。
